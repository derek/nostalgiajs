From 1995 the contact form on a great many small websites was one free Perl script, and the script sent its mail to whatever address the web page told it to.

<input type=hidden
  name="recipient"
  value="email@your.host.com">

That tag comes from the Readme of FormMail, which prints it on one line; I have broken it to fit. "There is only one form field that you must have in your form, for FormMail to work correctly," the Readme says, and names this one. You put your address in a hidden input, pointed the form at FormMail.pl, and whatever a visitor typed arrived in your inbox.

FormMail was written by Matt Wright and given away at Matt's Script Archive. I knew it the way most people now do, as the script spammers abused and Perl programmers warned you off. What I had not understood until I read its change log, the security advisory written against it and its author's own account was how the trouble was built into the selling point, how hard the author was to find when it mattered, and that the people who wrote the replacement ended up with their download links on the author's own site.

A mail gateway for people without a cgi-bin

Wright tells the beginning on a page of the archive. The scripts went up from 1995, when Wright was still in high school and had no formal training in programming: "I released the code as I learned, hoping others would find it useful." The history at the end of the Readme dates version 1.0 of FormMail to June 11, 1995. The header of the script itself says June 9.

A form needs a program on the server to receive it, and the Readme's list of possible uses describes who had trouble with that: people who wanted a form mailed to them and did not know how to write the program, and webmasters who wanted their users to have forms without giving each of them a cgi-bin directory. FormMail's answer was one script, installed once, that every form on the server could be aimed at, with its options set in hidden fields of the form itself. Wright's page for the script calls this "the perfect system-wide solution for allowing users form-based user feedback capabilities without the risks of allowing freedom of CGI access." So FormMail was offered to administrators partly as a safety measure.

It had security fixes almost at once. Version 1.1, on August 3, 1995, closed a hole that let users run commands under the server's user ID, with thanks to a Paul Phillips who noticed it. Version 1.3, in January 1996, closed the door on strangers' forms, and its history entry is my favourite line in the file: "Security hole, which allowed any user on any system to bum off of your formmail script, has been plugged up with the @referers variable." You listed your own domains, and the script checked that the browser's Referer header named one of them. That decided whose forms could use your copy. It put no limit on where the mail could go.

Then came version 1.6, on May 2, 1997, and after it nothing for more than four years. Wright's page about the archive says most of its scripts stopped being updated after 1996, apart from major security flaws and bugs. The downloads did not stop. Wright's page for the script claims FormMail was "downloaded over 2,000,000 times since 1997" and may be the most used CGI program on the internet. Those are Wright's own figures, and I have no second source for them.

How FormMail 1.6 became a mail relay

The best account of what went wrong is an advisory posted to the Bugtraq mailing list on January 23, 2002, by Ronald F. Guilmette and Justin Mason, who is identified in it as the maintainer of SpamAssassin. Abuse, it says, "was rendered trivial by the script's total reliance on information transmitted by the web client to the web server", both to decide whether a request was allowed and to decide where the mail went.

This is the referer check, from the 2009 release of the script; the advisory quotes the same lines from the version current in 2002.

if ($ENV{'HTTP_REFERER'}) {
    foreach $referer (@referers) {
        if ($ENV{'HTTP_REFERER'} =~ m|https?://([^/]*)$referer|i) {
            $check_referer = 1;
            last;
        }
    }
}
else {
    $check_referer = 1;
}

Read the else. A request with no Referer header at all is waved through. The advisory expects most attackers to do exactly that, and adds in a footnote that the Lynx browser had a -noreferer switch for the purpose. If you could not drop the header, the pattern would still pass any URL that had an allowed domain somewhere in it, such as http://www.attacker.tld/myform.html?http://www.victim.com/. That mattered to anyone attacking from a browser: the authors note that JavaScript's submit() always sent a Referer and they had found no way to stop it. Guilmette's covering note points to a working demonstration, written entirely in client-side JavaScript, of an exploit for FormMail 1.6. I have not seen that page.

Once past that check, in the version that had spread, there was no second one. The Readme's history shows no list of permitted recipients until version 1.7, in 2001. Until then the address in the hidden field was simply believed, and a stranger needed only the URL of your FormMail.pl and a request that set recipient to anyone they liked. The script piped the message to the mail program on the same machine, which treated it as a trusted local user, and the advisory points out that a recipient could trace such a message "only as far as the web server that hosts the FormMail script."

The advisory dates the discovery loosely, to some time between the release of 1.6 and March 2001, by when spammers were using installed copies as what it calls the functional equivalent of anonymising open mail relays. In September 2001, on the Security Incidents list, Jay D. Dyson answered a report of probes for the script by saying that many had succeeded at one agency Dyson advised, and offered a theory: "spammers have tired of simply looking for open relays and are now looking for other avenues by which they can abuse third-party mail systems".

FormMail did have one accidental defence. Every message it sent began with its own line, "Below is the result of your feedback form." The advisory's authors assume, with what reads like some pleasure, that this habit annoyed spammers enough to explain why they had generally preferred ordinary open relays. Even a spammer has brand standards.

Three patches in a week, then silence

The Readme's history shows Wright coming back to the script in the summer of 2001, and it shows the chase. Version 1.7, on July 27, added @recipients, a list kept in the script on the server of where mail was allowed to go, and the entry says outright that it was there to defeat spamming. Version 1.8 followed on August 2, because "under certain cases in v1.7, spam could still get through by appending a legit recipient to the list of intended spam victims." Version 1.9 came the next day, with a check against newline characters in the subject field. That is three releases in a week, each fixing what the one before had missed.

The January 2002 advisory was about 1.9, and it found that the job was not finished. It goes further than the Readme does, and says versions before 1.9 did no checking of the recipient at all; I have not seen the 1.7 or 1.8 code, so I can only report that the two disagree. On 1.9 itself the advisory is specific. The referer check was unchanged. The recipient check compared only the end of the address against the allowed list, so if you had allowed your whole domain, an address such as user%somewhere.tld@ourdomain.tld passed. That is what the advisory calls the old Sendmail percent hack, a form of address that the mail server next to FormMail would, the authors explain, almost certainly accept and send on to user@somewhere.tld. And the newline check covered the subject only. The sender's address and name went into the header through this line, unfiltered:

print MAIL "From: $Config{'email'} ($Config{'realname'})\n";

Put a newline in the email field and you were writing mail headers of your own. The advisory's example sets it to IGNORED\nCc: user@somewhere.tld,..., where \n stands for a real newline, and then shows the same trick supplying a subject and an opening line of body text, which pushes FormMail's tell-tale sentence down the page. The sample text is "MAKE MONEY FAST!!!".

The part I did not know is in the section headed "Notification". Both authors wrote to the address on the FormMail home page more than five working days before publishing and got no answer, and had no more luck by telephone. Guilmette posted a patched copy, labelled 1.9s, warned in capitals that nobody had reviewed or even tested it, and explained why: "I have been totally unable to even get into contact with the original FormMail author, so you may be sure that he has not even seen this (1.9s) version of his script." A script its author thought might be the most used CGI program on the internet had, as far as two security researchers could tell that month, nobody at the other end. I have only their side of this. Nothing I read gives Wright's.

The answer came just under three months later. The history's entry for version 1.91, dated April 19, 2002, concedes the point in its first sentence: "The same vulnerability that was patched in 1.9 with the subject field still existed in the email and realname fields." The same release tightened the default recipient patterns against the percent hack, and the Readme's overview says it addresses the worst problems made public in an advisory it cites by URL, a PDF on Guilmette's site that I could not open and that looks to be this one. The script's page still carries the banner from that week, a security update dated April 19, 2002, telling everyone on an earlier version, 1.6 included, to upgrade immediately.

Why one script sat on so many servers

The first force was convenience, and I'd argue it cannot be separated from the flaw. A script that takes its settings from the HTML can be used by someone who cannot edit a script. A form handler configured by the page has to trust the page, and the page comes from the browser.

The second was that popularity fed itself. Dave Cross laid this out in "Finding CGI Scripts", an article the copy on the Perl Hacks site says first ran on perl.com in January 2002. Searching for CGI scripts put Matt's Script Archive in the first two results, and the people searching were not programmers who could judge the Perl they downloaded. So the best-known archive got the links, the links got it the ranking, and, as Cross put it, "at no point does any kind of quality control enter into the process."

The third was time. Perl changed a great deal after 1995, and the script mostly did not. Cross's checklist for a trustworthy script (warnings, use strict, taint mode, the standard CGI.pm module, recent updates) is a list of things FormMail lacked, and the nms project's own site, which I'll come to, was blunter about the archive's code. Wright's page does not really argue. "My interests and activies have moved on", it says, typo and all, and it adds that there has been no time to update the scripts. A person who wrote something useful in high school is allowed to grow up and do other things. The web had no arrangement for what happens to two million downloads when they do. Dyson's theory supplies the trigger: if spammers came to form scripts because the lists that tracked open relays had shut or started charging, the hole sat in plain sight for years and became valuable only when the easier doors closed. That is one administrator's reading, from one mailing-list post.

The London Perl Mongers' drop-in replacement

The fix that lasted did not come from the archive. Cross's article says that in the summer of 2001 a group of London Perl Mongers began to wonder what it would take to write replacements for the CGI programs in common use. The article says "we" throughout, so I take Cross to have been one of them. They called the project nms and chose Wright's scripts as the target, for a reason Cross was careful about: "This wasn't because Matt Wright's scripts were the worst out there, but simply that they were the most commonly used."

What I admire is the constraint they set themselves. The scripts had to be drop-in replacements, so that anyone using one of Wright's could put the new one in its place and carry on, and the nms site is clear that the audience was webmasters who might not know much Perl at all. And they could use no modules beyond those that ship with Perl, even though that meant the form mailer ended up "talking directly to sendmail" where good practice would have used a mail module. Cross's reasoning was that the audience was on hosted servers, often without shell access. A secure script nobody could install would protect nobody.

The other rule was about readers of the code. The nms site complains that "one of the worst legacies of Matt's scripts is that people use them to learn Perl", so every replacement had to run clean under use strict with warnings and taint checking on. Free scripts were the View Source of the server side: people opened them to change a colour and copied the habits.

It was not a clean victory, and the sources say so themselves. Cross admitted in January 2002 that "the one advantage that Matt's scripts have over ours is that they've had many years of testing on a large number of Web sites." The Bugtraq advisory, the same month, names nms as one of two fixed versions of FormMail in circulation and says neither dealt with every problem it raised. The name was a small embarrassment too. By Cross's account it began as a disparaging remark about one of the existing archives, and by the time the group thought better of that, the initials had stuck. Officially they stand for nothing.

For everyone else, coping meant the advice Dyson gave that September: don't run a web-to-mail gateway "unless you've got your script configured to allow only specific recipients." The nms news page records how far that advice had to travel. It says SecurityFocus put attacks on Wright's FormMail third in its list of top attacks for the first quarter of 2002. I could not open SecurityFocus's own list, so that is nms's report of it.

What survives of FormMail

The author recommended the replacement, and hosts it. The nms site says that in May 2002 Wright redesigned the archive and added a page about the project. That page is still there, and it is not grudging. It recommends the nms versions to anyone who wants to learn CGI programming, and says of the archive's own code that it is "not representative of how even I would code these days." Below that, the archive offers the nms files for download from its own server, fourteen of them, each listed against the script of Wright's that it replaces. The originals stay up, Wright explains, because they still work for many people.

The nms site quotes Wright's page and adds one line of its own: "I call that a good result :)".

The referer check is still in the script, with a label on it. The last release I could find is 1.93, dated July 14, 2009, two months after three researchers at ush.it reported cross-site scripting and response-splitting holes in 1.92; the script's header credits them by name. The code I quoted earlier is from that release, else branch included. What changed is the documentation around it. The Readme now describes the check as a remnant of the days when it was used for security, and says: "This is not a security check. Referer headers can EASILY be faked."

FormMail turned into a service. The archive's pages advertise FormMail.com, a hosted form processor for people who would rather not install anything, with plans "at less than $1 per month". The script's first pitch was that one copy could serve every form on a server. The hosted version is that idea with the server moved to the author's side.

And old copies were still in service long afterwards. Under Cross's article there is a comment from March 2017 by a reader who mentions having used the archive's scripts as a teacher, and who had "hundreds of scripts that send email using the old formmail.pl code" and server logs showing thousands of messages going out. The comment does not say how the mail was being sent, or whether those scripts were Wright's FormMail or things built on it. Cross replied within minutes and told the reader to start by taking the compromised program off the server. That was more than fifteen years after the first anti-spam patch.

The takeaway

FormMail believed what the browser sent, which is how a great deal of the early web went wrong. The design that let anyone use it without touching a script, with the destination written in the page, was the design that let any stranger use it too, and the patches of 2001 and 2002 were attempts to keep the convenience while taking back the trust. What I find worth remembering is how the ending went. The people who wrote the replacement were rude about the code and careful about the users, they built it to be swapped in by people who could not read it, and the author put it on the front counter next to the original and said plainly that it was the one to learn from.

The hidden field is still in the Readme, and a form written for FormMail would still need it. The difference is one sentence further up the same file: "@recipients is the most important variable you need to configure." The page still says where the mail should go. The script no longer takes its word for it.
