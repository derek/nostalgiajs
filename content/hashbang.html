For a few years around 2011, some of the busiest addresses on the web contained two characters which guaranteed that the server would never learn which page you had asked for.

twitter.com/timbray
twitter.com/#!/timbray

That pair comes from Tim Bray, who wrote in February 2011 of getting "madder and madder" now that the first address "has become" the second. The essay is called Broken Links. Its own URL ends in Hash-Blecch, which tells you the mood.

The two characters were called the hashbang, the name Unix people already used for the #! at the top of a shell script. They were not Twitter's invention. They were half of a deal Google had offered to sites built with Ajax: put #! in your URLs, and our crawler will ask you for the same page under a different, uglier name. This essay is about how that deal came to exist, what happened to a publisher that took it, and why the industry then moved page rendering back to the server it had just left.

The part after the #

The hash sign started as a way to point at a spot inside a page. Jeni Tennison's long essay Hash URIs, the calmest thing written during this argument, traces the definition through the RFCs. In 1994 the thing after the hash was an anchor to scroll to. By 1998, in the text Tennison quotes from RFC 2396, it was "additional reference information to be interpreted by the user agent after the retrieval action has been successfully completed". The current rule is RFC 3986, from January 2005, which says the fragment is "separated from the rest of the URI prior to a dereference" and is handled "solely by the user agent".

In plain terms: the browser keeps it. You can check with any URL parser. This runs in Node:

var u = new URL("http://twitter.com/#!/timbray");
u.pathname  // "/"
u.hash      // "#!/timbray"

I also pointed curl at a local server with that path and fragment. The server logged GET / and nothing more.

For a document, that is a sensible design. For an Ajax application it was the only loose floorboard in the building. Once a page fetched its content with XMLHttpRequest and never reloaded, the address bar stopped changing. The back button left the application altogether, and you could not bookmark or send anyone the screen you were looking at. The Q&A Jesse James Garrett appended to the essay that named Ajax listed the back button among its open questions. The fragment was the one piece of a URL that script could rewrite without triggering a page load, so that is where application state went.

Getting it to work took effort. In September 2005 Brad Neuberg counted five libraries and techniques for "bookmarking and the back button in AJAX applications", Neuberg's own Really Simple History among them. Browsers had no event to tell you the fragment had changed, so libraries looked at location.hash on a timer. The W3C Technical Architecture Group's draft finding Repurposing the Hash Sign for the New Web, which lists a first version from April 2009, gave the appeal ("the characters in the URI bar after the hash can be changed without causing the page to be reloaded") and the cost: "without running JavaScript, the URI has no meaning."

October 2009: Google's offer

A URI with no meaning to anything but a browser is a problem for a company whose product reads the web with something that is not a browser. On October 7, 2009, the Google Webmaster Central blog published A proposal for making AJAX crawlable. It said search engines "traditionally are not able to access any of the content" on Ajax sites, and added a number: "almost 70% of the websites we know about use JavaScript in some form or another."

The proposal had three moving parts. First, a site marks the fragments that represent real, linkable states by starting them with a token. "Based on a review of current URLs on the web, we propose using "!" (an exclamation point) as the token for this." Second, because "URL fragments are never sent with requests to servers", the crawler rewrites the address so the state travels in the query string, under a second token chosen the same way. Third, the site answers that rewritten address with ordinary HTML. The post's own worked example:

https://example.com/dictionary.html#AJAX
https://example.com/dictionary.html#!AJAX
https://example.com/dictionary.html?_escaped_fragment_=AJAX

The first line is what an Ajax site had. The second is what it should publish. The third is what the crawler would fetch, after which the search results would show the second again.

How was the site to produce HTML for a page that existed only after its JavaScript ran? The proposal's answer was: "Use a headless browser that outputs an HTML snapshot on your web server". The server was to run a browser, load its own application in it, and send the crawler the result. Among the stated goals was "Users and search engines see the same content (no cloaking)". I'll come back to both of those.

Mike Davies, whose essay is the centre of the next section, pointed out what Google had been telling people. Its Webmaster Central blog had advised in 2007 that anyone starting from scratch should "build your site's structure and navigation using only HTML" and add Ajax afterwards. The #! scheme was, in Davies's word, a "lifeline" for sites that had already gone the other way. Within a year, a very large site read the workaround as an architecture.

Twitter takes the deal

Twitter relaunched its website in September 2010 as a JavaScript application, known as #newtwitter. Ben Cherry, a front-end engineer on the project, explained the URL change that December:

Many people have noticed that the new Twitter.com brought a small change to the site's URL structure: the introduction of a /#!/ at the front of the path. This is a simple change that most front-end engineers are already familiar with, but with huge performance savings.

Cherry continued that the #! "is there to comply with Google's Ajax crawling specification, so we don't lose out on search engine rankings with the new scheme." Moving from a profile to a tweet no longer threw away the page; script fetched JSON from Twitter's API and drew it.

Tennison tested what the site did with each form of address in early 2011. A logged-in browser asking for the plain URL of a tweet got a 302 redirect to the #! version. Asking for http://twitter.com/?_escaped_fragment_=/JeniT/status/35634274132561921 got a 301 back to the plain one. And curl on the hashbang URL got the home page, with, in Tennison's words, "no idea that the original hash-bang URI was supposed to give me anything different". Twitter had kept its old server-rendered pages and bolted the application on top. The next adopter kept its spare for crawlers only.

Monday, February 7, 2011

Gawker Media rolled out a redesign across its sites, Lifehacker and Gizmodo among them, in early February 2011. The day after it went wrong, Mike Davies published Breaking the Web with hash-bangs. The opening is a fair summary of the incident:

Lifehacker, along with every other Gawker property, experienced a lengthy site-outage on Monday over a misbehaving piece of JavaScript. Gawker sites were reduced to being an empty homepage layout with zero content, functionality, ads, or even legal disclaimer wording.

Davies gives the before and after for one article:

http://lifehacker.com/5753509/hello-world-this-is-the-new-lifehacker
http://lifehacker.com/#!5753509/hello-world-this-is-the-new-lifehacker

and then the line everyone quoted: "So Sunday Lifehacker was a 1 million page site, today it's a one page site with 1 million fragment identifiers." Every URL on every Gawker site now asked the server for the same thing, the home page, and trusted script to do the rest. When the script failed to load, by Davies's account for five hours, there was no rest. Readers arriving from Google got page furniture, and I'd expect View Source showed them little more.

On February 8 The Next Web reported that Google News had not indexed a Gawker story in 24 hours; a Gawker director called it a bug they hoped to fix soon. Davies added a two-line demonstration for people who prefer evidence to adjectives:

$ curl http://lifehacker.com/#!5753509/hello-world- \
  this-is-the-new-lifehacker | grep "Hello"
$

The second prompt, with nothing above it, is the result.

Why sensible people did this

It's easy to tell this as a story about engineers who forgot how URLs work. They hadn't.

It was faster, once you were in. A page of 2010 was mostly header, sidebar and script, repeated on every click. Loading that shell once and swapping the middle saved real time and real bandwidth. Tennison lists it among the advantages: hash URIs "give caching (and therefore performance) boosts", since everybody requests the same wrapper.

They believed they were shipping an application. Four days after the Gawker outage, Cherry published Thoughts on the Hashbang, the best defence anyone wrote. Its argument is that twitter.com "is no longer a collection of Web pages" but "simply an application that you happen to launch by pointing a browser" at it. A desktop program owes you no URLs at all. On that view the hash was a bonus: "The hashbang is in the unfortunate position of being the messenger".

The browsers offered nothing else. The proper fix already existed on paper. HTML5's history.pushState() lets script change the whole path without a reload. MDN's compatibility data puts it in Chrome 5 and Safari 5, both from mid-2010, and in Firefox 4, released in March 2011. Internet Explorer 9 came out the same month without it, and Internet Explorer did not get it until version 10 in October 2012. Cherry says Twitter built the History API integration and would have shipped it "on day one" but for a browser bug they found. For any site with a large Internet Explorer audience, which in 2011 was any site, the fragment was the only mechanism that worked everywhere.

Google had removed the penalty. Before October 2009, a commercial publisher that hid its articles behind fragments would have vanished from search, and nobody would have proposed it twice. The crawling scheme made the choice survivable. I'd argue that is the real effect of the proposal: it was written to rescue existing Ajax sites and it worked as a permission slip for new ones.

The argument, and the workarounds

The week after the outage produced one of the better public arguments the trade has had. Bray's piece put the objection as a contract. A link used to mean: here is a string, send it to a server, get back a representation. Now it meant sending part of the string and "being able to run the code the server sends you". Bray called the Google scheme "a hideous kludge". Jeremy Keith's Going Postel made the robustness point: HTML and CSS skip what they don't understand, while in JavaScript "a simple typo could potentially cause an entire script to fail". Ben Ward's essay "Hash, Bang, Wallop" no longer loads at any address I could find, but Davies quotes an earlier rule of thumb of Ward's: "If site content doesn't load through curl it's broken".

Tennison's conclusion was the one that held up. Hash-bang URIs would "be around for several years", so use them only for browsers that have JavaScript and lack the History API, publish the plain URL as the one people share, and make the _escaped_fragment_ form redirect to it. One warning in that essay has aged well: adopt hash-bangs as your primary URLs and you would be "reliant in perpetuity on Javascript routing" to decode them.

Libraries took the same line and automated it. Backbone 0.5.0, released on July 1, 2011, added pushState as an opt-in. The middle of the start function in its source is the whole history of the problem in nine lines:

// Depending on whether we're using pushState or hashes, and whether
// 'onhashchange' is supported, determine how we check the URL state.
if (this._hasPushState) {
  $(window).bind('popstate', this.checkUrl);
} else if ('onhashchange' in window && !oldIE) {
  $(window).bind('hashchange', this.checkUrl);
} else {
  setInterval(this.checkUrl, this.interval);
}

Read it bottom to top for the chronology. The last branch is 2005: poll the address bar, here every 50 milliseconds, with a hidden iframe a few lines earlier for old Internet Explorer. The middle is the hashchange event, which MDN's data lists in Internet Explorer 8, a 2009 browser. The top is the History API. The browser that was last to pushState was early to the event that made hash routing pleasant. Nobody planned that as a trap, I assume, but it worked like one.

Twitter turns around

In February 2012 Dan Webb, then an engineer at Twitter, tweeted about "undoing twitters hashbang URLs", as Ubergizmo reported. Webb's 2011 essay on the subject, "It's About The Hashbangs", is gone from Webb's site, so I can only name it.

On May 29, 2012, Twitter's engineering blog published "Improving performance on twitter.com", by Webb. The post would not load for me at its current address, so I'm quoting it from two reports that reproduced parts of it. NBC News carried the headline claim:

To improve the twitter.com experience for everyone, we've been working to take back control of our front-end performance by moving the rendering to the server. This has allowed us to drop our initial page load times to 1/5th of what they were previously and reduce differences in performance across browsers.

.net magazine quoted the part about URLs:

With hashbang URLs, the browser needs to download an HTML page, download and execute some JavaScript, recognize the hashbang path (which is only visible to the browser), then fetch and render the content for that URL…

Set that beside Cherry's "huge performance savings" from seventeen months earlier. Both were right. The hashbang made the second click fast and the first one slow, and every visit that begins with a link to a single tweet is a first click. Twitter's measure was the time until you could read one tweet, which The Next Web reported as "time to first tweet". The performance people had a new metric and the hashbang failed it.

Google took longer. On October 14, 2015 it published Deprecating our AJAX crawling scheme: "Times have changed", it said, and Googlebot was now "generally able to render and understand your web pages like modern browsers". The advice was progressive enhancement and pushState. A follow-up in December 2017 said that from the second quarter of 2018 Google would stop requesting _escaped_fragment_ URLs and render the #! pages itself.

What it left behind

The snapshot became the product. Under Google's scheme the server-rendered HTML was a side dish for robots, and the JavaScript application was the meal. Current frameworks serve the snapshot to everyone and then start the application on top of it. React's documentation for hydrateRoot describes attaching "to existing HTML that was already rendered by React in a server environment". The 2015 deprecation notice expected sites to "pre-render pages for performance benefits for users", and said that doing it only for Googlebot "is considered cloaking". The 2009 proposal had promised no cloaking, and then specified a second URL that only crawlers would ever request.

The data in the page source is older than you think. Cherry's 2010 article describes Twitter's Rails server predicting the first API calls the script would make and "sending down the expected response in the initial page source", to seed a client-side cache. I read that as a direct ancestor of the serialized state that server-rendering frameworks embed in a page for hydration. The JavaScript-only Twitter was already server-rendering its data, if not its markup.

A hashbang link cannot be redirected by a server. This is Tennison's "in perpetuity" warning, and it follows from the first code sample in this essay. A moved page can answer its old address with a 301. A page that lived at /#!something never had an address the server could see, so every such link ever pasted into an email or a forum arrives as a request for the home page, and only script shipped on that home page can forward it. When I requested Davies's two Lifehacker addresses, the plain one was redirected with a 301 to a renamed address that answered 410 Gone, and the hashbang one answered 200 with the present-day front page.

The prefix outlived the scheme. AngularJS 1.6.0, released on December 8, 2016, changed the default prefix for its hash URLs "from the empty string "" to the bang "!"", so that mydomain.com/#/a/b/c "will become" mydomain.com/#!/a/b/c, in the words of its changelog. That was fourteen months after Google stopped recommending the convention.

Hash routing never left, and has an honest job. Vue Router still offers a hash mode, and its documentation states the trade in two sentences: because the fragment "is never sent to the server, it doesn't require any special treatment on the server level. It does however have a bad impact in SEO." React Router has createHashRouter. The mode is what you reach for on a static host that cannot be told to serve one file for every path, or, as the Vue docs say, when the app is loaded from a file:// URL. Those are applications in Cherry's sense, with no server to ask.

The takeaway

The hashbang was a reasonable patch on a browser limitation that got mistaken for a design. The limitation was real: until pushState reached every major browser, the fragment was the only part of an address script could change freely. Google's scheme was also a patch, on the crawler's side. Stack the two and you get a site whose every page depends on one script loading, which Gawker demonstrated to a large audience.

What I take from it is that a URL's value comes from how many kinds of client can use it, and that the server is the only party in a position to answer all of them. Twitter's engineers were right that they were building an application, and right that it was faster once it was running. They were also the ones who measured the first load and moved rendering back. The architecture most teams reach for now, a server-rendered page with an application started on top of it, is the compromise both sides of the 2011 argument were asking for. It took browsers shipping one API and about five years of everyone's patience to get there.
