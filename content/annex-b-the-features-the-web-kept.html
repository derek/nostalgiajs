The JavaScript standard has an appendix for the features it would delete if it could, and every browser is required to ship all of it.

"Hello, world".blink()
// "<blink>Hello, world</blink>"

That line runs today. I ran it in Node 22 and it printed exactly that string. No current browser makes the result blink, but the method that builds the tag is specified, tested and mandatory. Its definition is clause B.2.2.4 of the ECMAScript specification, in Annex B, "Additional ECMAScript Features for Web Browsers", and it is two steps long.

The annex is frank about its contents. Everything in it has "one or more undesirable characteristics and in the absence of legacy usage would be removed from this specification." The neighbours of blink() include escape(), substr(), a comment syntax made of HTML, and a method that lets you swap the pattern inside a live regular expression. Two residents already have essays of their own in this collection: getYear(), and document.all, the object that claims to be undefined. This essay is about the rest, and about why a standards committee keeps a careful, normative description of things it tells you not to use.

A language that shipped first

JavaScript went out in Netscape Navigator 2 before anyone had written a standard for it, and its first job was to write HTML. There was no DOM to speak of. You produced page content by calling document.write() with a string of markup, so the language came with helpers for building that string. A mirrored copy of Netscape's JavaScript reference from the Navigator 3 era lists anchor, big, blink, bold and the others, each marked "Implemented in Navigator 2.0." The entry for blink reads: "Causes a string to blink as if it were in a <BLINK> tag." Its example is the opening snippet of this essay with period furniture:

var worldString="Hello, world"
document.write(worldString.blink())
document.write("<P>" + worldString.bold())

The same reference has escape, also from Navigator 2.0: "Returns the ASCII encoding of an argument in the ISO Latin-1 character set." You used it to put a form value into a URL or a cookie. The example given is escape("Hello, World"), which returns "Hello%2C%20World", and still does.

Navigator 2 also had to live beside browsers that had never heard of scripts. Allen Wirfs-Brock and Brendan Eich tell the story in "JavaScript: The First 20 Years". Netscape 1 and Mosaic, meeting a <script> element, displayed its contents as text. The way to stop them was to wrap the script in an HTML comment, but then the comment markers were a syntax error in JavaScript. So, the authors write, "Brendan Eich made JavaScript 1.0 accept <!-- as the start of a single line comment, equivalent to //." You closed the block with // -->, and for years that wrapper was the first thing anybody learned by reading other people's pages.

JavaScript 1.2, in 1997, added a second layer. The history paper's list of new features includes regular expressions, a batch of string methods, and the "__proto__ pseudo property of all objects", which let a program read and replace an object's prototype. Of the string methods it says that match, replace and substr "came from Perl." The language already had substring, and the same release brought slice from Python. That made three ways to cut a string, each with its own opinion about what the second argument means.

1999: an annex called Compatibility

The first edition of ECMA-262, from June 1997, simply wrote some of this down. escape and unescape are in its main text, as sections 15.1.2.4 and 15.1.2.5. So are octal literals: a number written with a leading zero, like 010, is eight. The HTML methods, the HTML comments and substr are not mentioned. Browsers implemented them anyway.

Annex B first appears in the third edition, adopted in December 1999. It was not yet called what it is called now. Its title is one word, "Compatibility", and it is marked "(informative)", meaning nobody has to follow it. It runs to a few pages. Section B.1 holds octal literals and octal string escapes, which "have been removed from this edition of ECMAScript." Section B.2 holds six properties: escape, unescape, substr, getYear, setYear and toGMTString. The introduction to B.2 is a piece of committee prose I admire: the annex "suggests uniform semantics for such properties without making the properties or their semantics part of this standard." It is a standard's description of things that are not in the standard.

For escape this was a demotion with a replacement attached. The third edition is where encodeURIComponent and its three siblings arrive. The reason is in the algorithm, and it has barely changed since 1997. escape works one 16-bit code unit at a time. A value under 256 becomes %XX and anything larger becomes %uXXXX, a format the annex itself says is only "partly based on" the URL standard. Run it now:

escape("ä")              // "%E4"
escape("ć")              // "%u0107"
encodeURIComponent("ä")  // "%C3%A4"
escape("a+b c")          // "a+b%20c"

The first answer is Latin-1, the second is an invention, and the third is UTF-8, which is what servers came to expect. The fourth is the quiet one. escape leaves + alone, and a server decoding a form submission reads + as a space. A "C++" typed into a search box built this way would arrive as "C" followed by two blanks. The hidden-iframe request shown elsewhere in this collection builds its URL with escape(name), because in 2000 that is what everybody did.

substr took the opposite route. It had never been in the standard, so the annex was its way in, on probation. The trouble with it was never that it was broken. Here are the three Perl and Python cousins side by side:

"Mozilla".substr(1, 2)     // "oz"
"Mozilla".substring(1, 2)  // "o"
"Mozilla".slice(1, 2)      // "o"

substr takes a start and a length. The other two take a start and an end. A language needs at most one of these conventions, and JavaScript had standardised the other one first.

The committee's hope in 1999, as the history paper tells it and as the getYear() essay quotes at more length, was that listing a feature in a non-normative annex would mark it as deprecated and free implementations to drop it. The authors call that expectation naïve. No browser dropped anything.

Why nothing ever leaves

The author of the page is not the person who gets hurt. The history paper puts the constraint as a slogan, "Don't break the Web!", and then explains it. Pages are stored as source and reinterpreted on every visit, and many "are unmaintained by their original creators but still actively used." Change what substr returns and the people who notice are readers of a page whose author left in 2003. They cannot fix it. They can only decide your browser is the broken one.

No vendor can afford to go first. The paper credits Eich with the name "Browser Game Theory" for this. Two of the rules it lists: "Breaking-changes (even bug fixes) can drive away users," and "New browsers must conform to what is already there." A browser that removed escape() on principle would lose the pages that call it and gain nothing a user could see. So every engine kept every feature, and each new engine had to copy them, bugs and all, from the ones before.

An unspecified feature is worse than an ugly one. This is the argument that eventually changed the annex. If four engines must all support functions declared inside if blocks, and the standard refuses to say what those mean, then each engine guesses. The history paper says the third edition "had intentionally excluded" such declarations, that implementations "allowed such declarations" regardless, and that "each major-browser implementation gave them different semantics." Silence did not make the feature go away. It made it non-portable.

The committee ruled out a clean break. A new version of the language could have opted out of the old rubbish with a mode switch. The paper describes how that idea lost: in 2012 the committee agreed to try "One JavaScript", in which programmers should be able to think "without thinking about modes, versions, or dialects." If there is one language and old pages must keep running, the old features are part of that language whether you like them or not.

2015: the annex becomes law

The sixth edition, ECMAScript 2015, is where the annex gets its present name and its teeth. The 5.1 edition of 2011 still calls it "Compatibility" and still marks it informative. Four years later it is "Additional ECMAScript Features for Web Browsers", marked "(normative)", and it opens by saying its contents "are required when the ECMAScript host is a web browser." It also grew. In came __proto__, RegExp.prototype.compile, the thirteen HTML methods, the comment syntax, a looser regular expression grammar, and several pages on functions in blocks.

The comments are the neatest case. Eich's 1995 accommodation for Netscape 1 had never been documented as part of the language. The history paper's verdict: "It took twenty years, but in 2015 they were added to the ECMAScript standard—eventually Web Reality always wins." The standardised version recognises --> at the start of a line as a comment too, so this is a complete, legal script, and evaluating it gives 2:

var x = 1;
<!-- hello, Netscape 1
x = x + 1;
--> goodbye
x

The HTML methods got an actual design decision on the way in. All thirteen go through one helper, CreateHTML, which emits lowercase tags and replaces any double quote in an attribute value with &quot;. So 'x'.anchor('a"b') gives <a name="a&quot;b">x</a>. The text between the tags is not escaped at all. This is a function from 1995 with half of a 2015 security review bolted on, which I find oddly touching.

Functions in blocks got the full treatment. The annex lists the specific patterns that happened to work the same in every browser, and then defines extra rules for sloppy-mode code so that those patterns keep working alongside the new block scoping. In practice:

function f(b) {
  if (b) { function g() {} }
  return typeof g;
}
f(true)   // "function"
f(false)  // "undefined"

The function g is declared in the block, and when the block runs, its value is also copied out to a var in the enclosing function. Nobody would design that. It is the intersection of what four engines did, written down so a fifth can match it.

RegExp.prototype.compile came in the same way. It re-initialises an existing regular expression object in place, so var r = /a/g; r.compile("b", "i") leaves r as /b/i. MDN's note on it is as dry as the spec: it "causes the otherwise immutable regex source and flags to become mutable, which may break user expectations."

Living with it: lint, aliases and smoosh

Developers coped the way JSLint had taught them to: agree not to use the bad parts, and have a tool enforce the agreement. Strict mode, from the fifth edition, made part of that official. Legacy octal literals are a syntax error in strict code, which you can check by evaluating "use strict"; 010. Documentation did the rest. MDN marks escape, substr and every HTML method as deprecated. It is also honest about how far that gets you. Its page for substr admits "there is no trivial way to migrate" old calls to slice or substring "without essentially writing a polyfill," because the three disagree on negative arguments.

The committee, for its part, learned to add a new name beside the old one. When string trimming was tidied up, the proposal noted that all major engines already shipped trimLeft and trimRight "without any standard specification." The standard names became trimStart and trimEnd, to match padStart, and the old names went into Annex B as aliases "required for web compatibility." In a current engine "".trimLeft === "".trimStart is true. They are one function with two property names, and its name is "trimStart".

The same force acts on features that do not exist yet, and the best-known case is from 2018. A proposal added Array.prototype.flatten. Firefox Nightly shipped it and a popular site broke. Mathias Bynens's "SmooshGate FAQ" explains the mechanism, which is a small masterpiece of bad luck. The MooTools library defines its own Array.prototype.flatten and then copies its array methods onto another prototype with a for-in loop. Assigning over a built-in method does not make it enumerable. So once browsers had a native flatten, MooTools's replacement was skipped by its own loop, and code depending on the copy failed. The proposal's author jokingly suggested the name smoosh instead, the joke "was not clear to everyone," and some people took the new name as settled.

The FAQ's answer to "why not just break the Web?" is the Annex B argument in two sentences: "Sure, in retrospect MooTools did the wrong thing — but breaking the web doesn't punish them, it punishes users. These users do not know what a moo tool is." In May 2018 Michael Ficarra brought the rename to the committee, and the meeting notes record the outcome in three words: "We choose flat." There is a jQuery-era moral in there about libraries that extend built-in prototypes, and it is why the method you call is an adjective.

What it left behind

The annex is shrinking, because its contents are being promoted. If you open today's Annex B looking for __proto__ or octal literals, they are gone. Two pull requests merged in the summer of 2021 moved them into the main body: one for __proto__ and one for the octal syntax. Object.prototype.__proto__ is now clause 20.1.3.8 of the chapter on fundamental objects, followed by __defineGetter__ and its three friends, both clauses under a coloured box that says "Normative Optional, Legacy". The conformance clause defines the label: legacy features have undesirable characteristics, but "their continued usage in existing applications prevents their removal from this specification." The discussion on the __proto__ pull request shows how fine the distinctions got. A summary there sorts the pieces into required or optional, and "icky" or not. The object-literal syntax came out as required and not icky. The accessor came out optional and icky. I'd read the whole trajectory as a slow admission. In 1999 these things were outside the standard, in 2015 they were a required appendix, and now they are scattered through the main text with a warning label. The annex's own introduction says so: some of its features are now "specified in the main body of this document."

escape() survived by being wrong in a useful way. Because unescape turns each %XX into one character with that byte's value, and encodeURIComponent produces UTF-8 bytes as %XX, chaining them gives you UTF-8 encoding for free. Johan Sundström posted the trick in July 2006:

function encode_utf8(s) {
  return unescape(encodeURIComponent(s));
}
function decode_utf8(s) {
  return decodeURIComponent(escape(s));
}

It works today: encode_utf8("é") is a two-character string holding the bytes C3 and A9. It became a familiar way to get non-ASCII text through btoa(), which accepts only characters up to 255. So a function deprecated in 1999 for mishandling Unicode picked up a second career as a Unicode converter, and that usage is one more reason it can never be removed. I'd guess a fair share of the escape calls still on the web are this idiom and not a URL at all.

Some old features are not even in the annex. After a match, RegExp.$1 holds the first captured group. Engines do this, and Node printed a for me after matching /(a)(b)/ against "ab". The specification does not mention it. A proposal to specify these static properties in Annex B reached Stage 3 in May 2017 and is still listed there. Its README says the draft "does not reflect what the implementations do, but what the editor thinks to be the least bad thing they ought to do in order to maintain web compatibility." At a status review in January 2026, the notes quote an earlier finding that implementers "have lost interest in implementing this proposal." Meanwhile the annex still takes new residents. Its last clause today, B.3.9, covers assignments like f() = 1, which web browsers must accept at parse time and reject only when the line runs. I checked: a function containing that line parses, and calling it throws a ReferenceError.

The real deprecation mechanism turned out to be new containers. Nothing was removed from old scripts. But the annex's comment syntax is "not allowed when parsing source text using the goal symbol Module", and when I gave Node a module containing <!-- it answered "HTML comments are not allowed in modules." Modules and class bodies are always strict, so they get no octal literals and none of the block-function compatibility rules either. The committee could not take anything away from the pages of 1998. It could decline to bring it along into each new kind of code, and it did. If you write only modules, you have been living in the cleaned-up language for years without a version switch ever being thrown.

The takeaway

Annex B is what a standard looks like after it accepts that it does not own its language. The committee tried ignoring these features, then listing them as optional, then requiring them in an appendix, and it is now folding them into the main text with a label. Each step made the document less tidy and the web more predictable, because the alternative to specifying substr was never a world without substr. It was four slightly different versions of it. A feature on the web is removed only when nobody's page calls it, and nobody can ever prove that.

The practical consequence runs forward as well as back. Every name a popular library puts on a built-in prototype, and every quirk enough pages lean on, is a future constraint on the language, which is how an array method came to be called flat. So the annex is best read as a warning about anything you publish to a platform that never ships a breaking release. The string that blinks will outlast the tag, the browser that invented it, and quite possibly the rest of us.
