One of the most argued-over tools in JavaScript's history was a program that told you which parts of the language to stop using, and it came with a warning label.

Warning! JSLint will hurt your feelings.

That notice sat at the top of the JSLint documentation, directly under the line "©2002 Douglas Crockford", in an older copy of the page that survives on a university course site. It was a comment in the program's source in the edition of March 2013, and it is in the current one. The help page at jslint.com still carries it, now with a list of symptoms: "Side effects may include headache, irritability, dizziness, snarkiness, stomach pain, defensiveness, dry mouth, cleaner code, and a reduced error rate."

It is a joke, and it was accurate. You pasted your script into a text box, pressed a button, and a program written by one person told you that code which ran in every browser was unacceptable. Some six years later the same person published the argument as a thin book, JavaScript: The Good Parts. Between them they changed what professional JavaScript looked like. They also started a fork, a fight about a semicolon and a licensing problem that took other people nine years to clean up.

Before: a language with a reputation

In 2001 Douglas Crockford put an essay on a personal website under the title "JavaScript: The World's Most Misunderstood Programming Language". The page has been revised since, and I quote it as it stands now. It is a list of reasons for the bad reputation, and most of them are not the language's fault. The name suggests a cut-down Java. The syntax hides what is underneath, which the essay calls "Lisp in C's Clothing." The early implementations were buggy, the standard was hard to read, and the books were worse: "Nearly all of the books about JavaScript are quite awful."

Crockford was not a web designer who had drifted into scripting. The biography on the same site lists eight years as Director of Technology at Lucasfilm and, in 2001 and 2002, a startup called State Software, building "an application framework for highly-interactive web applications." This was an experienced programmer who came to JavaScript late and had expected little. A companion piece, "A Survey of the JavaScript Programming Language", admits as much: "When JavaScript was first introduced, I dismissed it as being not worth my attention. Much later, I took another look at it and discovered that hidden in the browser was an excellent programming language."

The 2001 essay does have a section called "Design Errors," and it is short. The + operator both adds and concatenates. The with statement is error-prone. "Semicolon insertion was a huge mistake". Then comes the sentence that the next ten years grew out of: "Fortunately, many of these problems can be mitigated with a good lint program."

It helps to recall what checked your JavaScript at the time. Nothing did. There was no compiler, so a misspelled variable name was not an error. It was a new global variable. You learned the language by reading other people's pages and you found your mistakes with alert(), after the browser had already run them.

A minifier, a lint and a hundred pages

The tools came first. Crockford's site dates JSMin to 2001, and a later note says the name was the origin of the word as we use it: "I called the operation minification, and I named the first minifier program JSMin." JSMin comes back into the story eleven years later.

JSLint followed. The sources disagree by a year about when. Allen Wirfs-Brock and Brendan Eich, in "JavaScript: The First 20 Years", cite its web page as 2001 and call it "the first widely used linter utility for JavaScript." The JSHint project's own history says it "was first made publicly available in 2002," which matches the copyright line. Either way, it was written in JavaScript and it ran in the page: "Your script is not sent over the network."

The documentation was clear that this was more than a syntax checker. "JSLint defines a professional subset of JavaScript, a stricter language than that defined by" the standard, it said, and then: "JavaScript is a sloppy language, but inside it there is an elegant, better language. JSLint helps you to program in that better language and to avoid most of the slop."

The subset was specific. Every variable had to be declared, because "JavaScript's biggest problem is its dependence on global variables, particularly implied global variables." Every if and while needed braces. with was out. === was preferred to ==, and an option could forbid == altogether. Another option banned ++ and --, on the grounds that they "have been known to contribute to bad code by encouraging excessive trickiness." You chose your options with checkboxes on the page, or with a comment at the top of the file. This is the documentation's own example:

/*jslint nomen: true, debug: true,
    evil: false, onevar: true */

The option that controls whether eval is tolerated is named evil. The page also had a single button that set every checkbox to what the documentation called "the ideal settings." The button was labelled "Good Parts."

The rest arrived quickly. In December 2002, by the history paper's timeline, Crockford set up json.org and gave a name to a data format made from JavaScript's object and array literals. That is another story, though it is why the X in Ajax aged so badly. In 2005 Crockford joined Yahoo as a "Distinguished Architect," and by July 2006 was representing Yahoo at meetings of the ECMAScript committee. A month earlier came a short page called "Prototypal Inheritance in JavaScript", with a five-line function on it:

function object(o) {
    function F() {}
    F.prototype = o;
    return new F();
}

It makes a new object that inherits from an old one, with no constructor and no pretend classes.

Then the book. O'Reilly published JavaScript: The Good Parts in May 2008. The back cover copy, as Open Library records it, says the book "scrapes away these bad features to reveal a JavaScript subset that's more reliable, readable, and maintainable than the language as a whole." By the table of contents on the same record, the ten chapters on the good parts end before page 101. Then come Appendix A, "Awful Parts," Appendix B, "Bad Parts," and Appendix C, "JSLint." A language book whose main text fits in a hundred pages was a statement in itself.

The thesis is in the first chapter, in a passage Wikiquote preserves: "JavaScript is built on some very good ideas and a few very bad ones. The very good ideas include functions, loose typing, dynamic objects, and an expressive object literal notation. The bad ideas include a programming model based on global variables." Two months before the book, Crockford had published a sequel to the 2001 essay that puts the whole project in one line: "When you peel away the cruft, there is an expressive and powerful programming language there."

Why a list of prohibitions caught on

Ajax brought in programmers who expected a compiler. After 2005, people who had spent careers in Java and C# were told to write the browser half of the application. Crockford's 2008 essay puts it this way: "Ajax gave JavaScript a second chance." They were used to a compiler that objected before anyone ran the code, and the browser offered nothing of the kind. By 2013 JSLint's documentation said so directly: it "will reject programs that browsers will accept because JSLint is concerned with the quality of your code and browsers are not."

The language itself was frozen. The third edition of the standard is dated December 1999 and the fifth is dated December 2009. There is no fourth. In 2007 Crockford wrote, in a set of recommendations to the committee, that the language "hasn't changed in seven years," and meant it as praise: "This is what allowed Ajax to happen." If nothing can be added and nothing can be fixed, the only way left to improve a language is to agree not to use parts of it. I'd argue that is why the subset landed when it did. It was the one kind of language design that needed nobody's permission.

There was a platform behind it. A linter on a personal website is a curiosity. The same linter, recommended by a Distinguished Architect at Yahoo who also gave the lectures, sat on the standards committee and had named JSON, was something a tech lead could cite. Wirfs-Brock and Eich, describing the evangelists of that period, call Crockford "one of the most influential."

And the rules were not all the same kind of rule. An undeclared variable silently becoming a global is a bug. Preferring i += 1 to i++ is a taste. JSLint presented both in the same voice. Today's help page owns up to it in a section headed "Perfectly fine," which begins: "JSLint was designed to reject code that some would consider to be perfectly fine." Whether that was discipline or one person's preferences is what the argument was about.

The fork and the semicolon

For years the way to cope was the options. If you disagreed with a rule, there was usually a checkbox to tolerate what you were doing, and you wrote the result into a /*jslint */ comment. Then the tool got stricter. On February 20, 2011, Anton Kovalyov published a post called "Why I forked JSLint to JSHint." The original address no longer answers, but the text survives in a copy in a Disqus repository. JSLint, Kovalyov wrote, "has gotten uncomfortably opinionated and hostile towards your code. It is quickly transforming from a tool that helps developers to prevent bugs to a tool that makes sure you write your code like Douglas Crockford."

The evidence was a function from jQuery 1.4.2, which is still on jQuery's CDN:

	isEmptyObject: function( obj ) {
		for ( var name in obj ) {
			return false;
		}
		return true;
	},

"Can't see anything wrong with this snippet? Me neither. But JSLint refuses to proceed further, failing with an error that tells you to 'move "var" declarations to the top of the function'. What is even worse, there is no way to turn this behavior off." In the 2013 source the message is there, word for word, and the code that raises it calls a function named stop. JSHint had gone out two days before the post, and its pitch was a promise about governance: "it will always be a community-driven tool. Simply because a community of programmers working together is better than a single person working alone." The post opens with an epigraph attributed to Crockford: "Your sadly pathetic bleatings are harshing my mellow." A footnote quotes the language's creator, Brendan Eich, as having said, "JSLint can suck it."

A fork inherits everything, including the licence. JSLint's was the MIT licence with one sentence added: "The Software shall be used for Good, not Evil." The Free Software Foundation's licence list takes the sentence seriously: "The restriction might be unenforcible, but we cannot presume that. Thus, the license is nonfree." JSHint's maintainers spent years getting out from under it. Their account describes collecting contributor agreements and having six patches rewritten from scratch, three of them by volunteers who had never seen the code they were replacing. They finished in August 2020.

The loudest episode involved the minifier. On April 13, 2012, a user opened issue 3057 on Twitter's Bootstrap, reporting that bootstrap-dropdown.js broke after going through JSMin. Bootstrap's JavaScript was written without semicolons, and version 2.0.2 contained these two lines:

      clearMenus()
      !isActive && $parent.toggleClass('open')

As written, the line break ends the first statement. JSMin's documentation lists the characters before which it will keep a line break, because "JavaScript sometimes treats linefeeds as semicolons," and ! is not on the list. Remove the break and the two lines become one expression that does not parse. The maintainer who goes by fat replied that this was "a bug in jsmin" and suggested telling Crockford. Crockford turned up in the thread: "That is insanely stupid code. I am not going to dumb down JSMin for this case." And then: "Learn to use semicolons properly. ! is not intended to be a statement separator. ; is."

The thread drew a crowd, and on April 15 Eich wrote the referee's report, "The infernal semicolon." It declines to give either side the win. Eich agreed "with Doug's canonically grumpy tone if not his substance," said the && line was poor style, and corrected Crockford's claim that the code would break in a future edition. The moral was aimed at everyone: "ASI is (formally speaking) a syntactic error correction procedure. If you start to code as if it were a universal significant-newline rule, you will get into trouble." Bootstrap 2.0.3 has an if statement there instead.

The next step was to remove the opinions from the tool altogether. In July 2013 Nicholas C. Zakas introduced ESLint with a short history of the field: "A long time ago, JSLint was the state of the art in JavaScript linting technology. Then JSHint came along as a fork and took over due to increased flexibility." But JSHint had "no easy way to add additional rules," so the new tool would be one "where all rules are pluggable."

What it left behind

The subset became a mode of the language. The "use strict" directive in the fifth edition is, I'd argue, JSLint's idea moved into the engine. The history paper traces it to Crockford's recommendations to the committee, not to the tool: "ES5 strict mode is the direct end product of Douglas Crockford's goal of 'correcting mistakes and inconveniences' in JavaScript's design." The paper calls it "subtractive": "It does not add new features to ECMAScript; instead it removes problematic features." In strict mode with is a syntax error and assigning to an undeclared name throws, which settles two of JSLint's oldest complaints. Then it stopped being optional. The current specification says "Module code is always strict mode code" and that all parts of a class are too. So every file with an import in it runs in a dialect that, on my reading, began as a set of checkboxes on a web page.

The five-line function is a built-in. The prototypal inheritance page has a dated addendum from April 7, 2008. Crockford had decided a global function called object was a bad idea, and now preferred to write the same body as Object.create, guarded by if (typeof Object.create !== 'function'). That is twenty months before the fifth edition was published with an Object.create in it. Wirfs-Brock and Eich write that the standard function "was essentially the beget function with a property map added as an optional second parameter," beget being another of Crockford's names for it. The same edition added JSON.parse and JSON.stringify, and Crockford's json2.js still describes itself in those terms: "This file provides the ES5 JSON capability to ES3 systems."

Your lint configuration is written in JSLint's vocabulary. The old options table has a column of short names: eqeqeq, newcap, plusplus, bitwise, onevar. JSHint kept several of them as they were. ESLint, the clean break, has rules called eqeqeq, new-cap, no-plusplus, no-bitwise and one-var. I can't prove the descent rule by rule, but nobody arrives at "eqeqeq" twice by accident. It began as the name of a JSLint checkbox, and it is in a great many repositories today.

The fix for the opinions brought the opinions back. JSLint had one author, and its switches were that author's to add or remove. The remedy was a fork with more switches, and then a tool that was all switches. That moved the argument out of the tool and into every team's configuration file, where it could be held again for each project. The reaction to that is a tool like JavaScript Standard Style, whose front page promises "No configuration" and "No decisions to make." That is JSLint's position, and I'd argue it is the part JSLint had right all along: most of the value of a house style is that the argument is over. This particular heir settled the old argument the other way. Its documentation lists a sibling package, semistandard, described as "standard, with semicolons (if you must)."

Not everything was adopted. The history paper notes that automatic semicolon insertion was on Crockford's list for strict mode and stayed in the language, because "many developers preferred to code without explicit semicolons." And the language went on to add the class keyword that the prototypal essay had argued it did not need. JSLint itself is still published, now by a GitHub organisation and under the Unlicense, with no clause about evil. Its help page says "Some of ES6's features are good, so JSLint will recognize the good parts of ES6," and class is not in the list that follows. Among the options is one described as "Allow this."

The takeaway

JSLint and The Good Parts made one argument twice: JavaScript contained a good small language, and you could have it immediately by refusing to use the rest. In a decade when the standard did not move, that was the only improvement on offer, and it worked. It gave developers a reason to take the language seriously and gave their teams something to point at in code review. The delivery was one person's taste presented as law. The fork, the semicolon thread and the pluggable linter were all reactions to that.

What lasted is the subset more than the tool. The rules that were about bugs went into the language as strict mode, and strict mode is now compulsory for modules and classes. The helper functions became Object.create and JSON.parse. I doubt many people paste code into jslint.com any more, and nearly everyone writes something close to the dialect it defined. The rules it insisted on that did not win, such as mandatory semicolons and no ++, are still being argued about, usually by people who have never had their feelings hurt by the original.
